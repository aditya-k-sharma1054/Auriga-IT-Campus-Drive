# ParkOps — Database Schema Specification

## 1. Database choice

SQLite for the timed assessment build, accessed through Prisma.

Reason: real relational persistence with minimal environment setup and no external database dependency.

Production evolution: PostgreSQL is the likely production target if the application moves beyond the assessment.

## 2. Database conventions

- IDs: UUID strings generated by the application/Prisma.
- Currency: integer paise, never floating-point currency values.
- Timestamps: UTC in the database; convert for display in the UI.
- Enum-like values: Prisma enums where supported.
- All relations use foreign keys.

## 3. Prisma-style schema

```prisma
enum SpotType {
  COMPACT
  STANDARD
  EV
}

enum SpotStatus {
  AVAILABLE
  OCCUPIED
}

enum VehicleType {
  COMPACT
  STANDARD
  EV
}

enum SessionStatus {
  ACTIVE
  COMPLETED
}

model User {
  id           String   @id @default(uuid())
  name         String
  email        String   @unique
  passwordHash String
  garageId     String
  createdAt    DateTime @default(now())
  updatedAt    DateTime @updatedAt

  garage       Garage   @relation(fields: [garageId], references: [id], onDelete: Cascade)

  @@index([garageId])
}

model Garage {
  id                    String   @id @default(uuid())
  name                  String
  address               String
  firstHourRatePaisa    Int
  additionalHourRatePaisa Int
  dailyCapPaisa         Int
  createdAt             DateTime @default(now())
  updatedAt             DateTime @updatedAt

  users                 User[]
  spots                 ParkingSpot[]
  sessions              ParkingSession[]
}

model ParkingSpot {
  id          String     @id @default(uuid())
  garageId    String
  floor       Int
  number      String
  type        SpotType
  status      SpotStatus @default(AVAILABLE)
  createdAt   DateTime   @default(now())
  updatedAt   DateTime   @updatedAt

  garage      Garage     @relation(fields: [garageId], references: [id], onDelete: Cascade)
  sessions    ParkingSession[]

  @@unique([garageId, floor, number])
  @@index([garageId, type, status])
}

model ParkingSession {
  id           String        @id @default(uuid())
  garageId     String
  spotId       String
  plateNumber  String
  vehicleType  VehicleType
  checkedInAt  DateTime
  checkedOutAt DateTime?
  feePaisa     Int?
  status       SessionStatus @default(ACTIVE)
  createdAt    DateTime      @default(now())
  updatedAt    DateTime      @updatedAt

  garage       Garage        @relation(fields: [garageId], references: [id], onDelete: Cascade)
  spot         ParkingSpot   @relation(fields: [spotId], references: [id], onDelete: Restrict)

  @@index([garageId, status])
  @@index([garageId, plateNumber, status])
  @@index([garageId, checkedInAt])
  @@index([garageId, checkedOutAt])
}
```

## 4. Important SQLite/Prisma note

The schema intentionally does not create a simple compound unique constraint on `(garageId, plateNumber, status)` because that would incorrectly prevent multiple historical COMPLETED sessions for the same vehicle.

The active-plate invariant is enforced through an authenticated transaction plus a targeted active-session lookup. The parking write itself is also transactionally guarded.

## 5. Seed strategy

On a new garage, create a deterministic default inventory so the product is immediately usable.

Suggested default:

- 3 floors;
- 30 total spots;
- a mixture of COMPACT, STANDARD and EV;
- enough EV spots to demonstrate both available and occupied states.

Suggested default pricing only for demonstration:

- first hour: ₹50;
- additional hour: ₹30;
- daily cap: ₹250.

These numbers are implementation defaults, not values specified by the assessment brief.

## 6. Garage creation

Registration should create a garage context in the same logical operation as the initial user account creation, followed by default spot creation.

The garage must never be hard-coded to one fixed identity.

## 7. Data integrity rules

- Foreign keys enabled.
- Negative pricing values rejected at validation layer.
- Spot floor must be a positive integer.
- Spot number must be non-empty.
- Plate number must be normalized before persistence.
- Checkout cannot create a negative duration.
- Fee cannot be negative.
